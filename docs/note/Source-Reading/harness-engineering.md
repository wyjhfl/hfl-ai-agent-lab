# Harness Engineering 源码拆解

## 项目定位

Harness Engineering 在本知识库中被作为 Agent 工程化、执行质量、Trace、Evaluator、Feedback 和失败样本管理的学习对象。

相比普通 Agent Demo，它更值得关注的是：如何组织执行流程、如何记录执行过程、如何评估结果质量、如何形成反馈闭环。这些是 Agent 从 Demo 走向工程化系统的关键能力。

## 架构总览

从工程化 Agent 角度，Harness Engineering 可以拆成以下模块。这些是当前拆解视角，不代表已经确认真实源码类名：

- **Task / Run**：任务和执行实例的管理
- **Executor**：实际执行任务的模块
- **Trace Recorder**：执行过程的完整记录
- **Evaluator**：结果质量评估
- **Feedback Collector**：人工反馈和失败原因收集
- **Result Store**：执行结果的结构化存储
- **Error Handler**：错误处理和异常管理
- **Test Case / Benchmark**：测试用例和质量基准

## 核心运行链路

Harness Engineering 的核心运行链路可以描述为以下流程：

1. **创建任务或测试样本**：定义要执行的任务或测试用例
2. **分配执行 Run**：为任务创建一次具体执行实例，生成唯一的 run id
3. **Executor 执行任务**：执行器接收任务，驱动 Agent 完成任务
4. **记录执行轨迹**：记录输入、输出、工具调用、状态变化和关键决策摘要
5. **生成执行结果**：把执行结果结构化存储，包含成功/失败标记
6. **Evaluator 评估结果质量**：自动评估或人工评审结果是否符合预期
7. **收集失败原因和反馈**：记录失败的具体原因，收集改进建议
8. **沉淀为测试样本或优化依据**：把评估结果和失败样本沉淀为后续优化的基础

这个流程体现了工程化 Agent 的核心循环：执行、记录、评估、改进。

## 关键模块拆解

### Task / Run

任务和一次执行实例是两个不同层次的概念。Task 是用户请求，Run 是一次具体执行。

重点关注：

- Task 和 Run 的关系：一个 Task 是否可以多次 Run
- Run 的状态管理：pending、running、completed、failed
- Run 的唯一标识：是否有 run id 用于关联 Trace、日志和评测结果
- Run 的生命周期：从创建到完成的完整流程

Task 和 Run 的分离让系统能够支持重试、对比和回归测试。同一个 Task 可以多次 Run，每次 Run 的结果可以独立评估。

### Executor

Executor 是实际执行任务的模块。它接收任务，驱动 Agent 完成任务，产出执行结果。

重点关注：

- Executor 如何接收任务
- 如何驱动 Agent 执行
- 如何处理中间状态
- 如何生成最终结果
- 如何处理执行过程中的异常

Executor 应该是可替换的。不同的 Agent 实现可以使用不同的 Executor，但对外接口应该统一。这让系统能够对比不同 Agent 实现的质量。

### Trace Recorder

Trace 是执行过程的完整记录。Agent 项目需要记录执行过程，否则很难调试和优化。

重点关注：

- 是否记录每一步的输入和输出摘要
- 是否记录工具调用参数和结果
- 是否记录状态变化
- 是否有唯一的执行 ID
- Trace 数据如何存储和查询

Trace 记录的是执行轨迹，不是模型的内部推理过程。记录的内容应该包括：关键决策摘要、工具调用记录、状态变化记录、执行轨迹。这让调试和复盘成为可能。

### Evaluator

Evaluator 负责评估执行结果的质量。它是 Agent 质量闭环的核心。

重点关注：

- 如何判断任务是否完成
- 如何判断结果是否符合预期
- 是否有自动评分
- 是否有人类反馈入口
- 评估结果如何存储和查询

Evaluator 可以是自动的（基于规则或模型），也可以是人工的（人类评审）。好的 Evaluator 应该能够量化结果质量，而不仅仅是二元的通过/失败。

### Feedback Collector

优秀的 Agent 系统不应该只执行一次，而应该能从失败中获得改进信息。

重点关注：

- 失败是否会被记录
- 是否能生成改进建议
- 是否支持重新执行
- 是否能积累评测样本

Feedback Collector 把失败转化为改进信息。每次失败都应该被记录、归类、分析，转化为具体的优化行动。这让系统能够持续改进。

### Test Case / Benchmark

测试用例和质量基准是 Agent 质量保证的基础。

重点关注：

- 测试用例覆盖了哪些场景
- 测试用例的输入输出是什么
- 是否有边界案例测试
- 是否有回归测试
- 是否有质量基准

测试用例应该覆盖：正常路径、边界情况、错误处理。每次修改后用回归测试确保没有引入新问题。质量基准用于衡量系统的整体质量水平。

## 关键设计思想

### 每次执行生成 run id

为每次执行生成唯一的 run id，用于关联 Trace、日志和评测结果。这让调试和复盘成为可能：通过 run id 可以找到一次执行的完整记录。

### 执行结果和评估结果分离

执行结果是 Agent 的输出，评估结果是对输出质量的判断。两者应该分开存储，因为：

- 同一个执行结果可能被多次评估
- 评估标准可能随时间变化
- 执行结果和评估结果的生命周期不同

### 失败样本沉淀为评测集

每次失败都应该被记录、归类、分析，沉淀为评测样本。这让系统能够：

- 用失败样本做回归测试
- 用失败样本衡量改进效果
- 用失败样本发现系统弱点

### Trace 支持调试和复盘

Trace 不只是日志，而是结构化的执行轨迹。通过 Trace 可以：

- 定位执行失败的具体步骤
- 分析工具调用的参数和结果
- 理解状态变化的因果关系
- 对比不同执行的差异

### Evaluator 支持质量闭环

Evaluator 不只是打分，而是质量闭环的核心。通过 Evaluator 可以：

- 量化结果质量
- 发现质量问题
- 驱动优化方向
- 验证改进效果

## 可迁移到自己项目的设计

从 Harness Engineering 中可以迁移以下设计到自己的项目：

- **为每次执行生成 run id**：唯一标识一次执行，方便关联 Trace、日志和评测结果
- **记录完整的执行轨迹**：记录输入、输出、工具调用记录、状态变化记录和关键决策摘要
- **执行结果和评估结果分离**：执行结果和评估结果分开存储，各自独立演进
- **失败样本沉淀为优化依据**：每次失败都应该被记录、归类、分析，转化为具体的优化行动
- **评测集防止回退**：用评测集持续监控质量，每次修改后用回归测试确保没有引入新问题
- **Trace 结构化存储**：Trace 数据应该结构化存储，支持按 run id 查询、按步骤筛选、按时间排序

## 面试表达

### 表达一：Trace 与 Evaluation

> 我在学习 Harness Engineering 时，重点关注 Agent 工程化中的 Trace 和 Evaluation。因为 Agent 项目如果没有执行记录和质量评估，就很难从 Demo 走向可维护系统。我的理解是，Agent 不仅要能完成任务，还要能记录它怎么完成、哪里失败、后续如何改进。Trace 记录每次执行的完整轨迹，Evaluator 量化结果质量，失败样本沉淀为优化依据——这三者构成了 Agent 工程化的闭环。

### 表达二：工程化设计

> 从 Harness Engineering 中我学到的最重要的工程化设计是"执行结果和评估结果分离"。执行结果是 Agent 的输出，评估结果是对输出质量的判断，两者应该分开存储。这样做的好处是：同一个执行结果可以被多次评估（比如用不同的评估标准），评估标准可以随时间变化而不需要重新执行任务。另外，失败样本沉淀为评测集的设计也很关键——每次失败都应该被记录和分析，转化为回归测试用例，防止同样的问题再次出现。

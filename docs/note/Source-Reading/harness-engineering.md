# Harness Engineering 源码拆解

## 项目定位

Harness Engineering 更适合用来学习 Agent 工程化、执行质量、评测反馈和 Trace 机制。

相比普通 Agent Demo，它更值得关注的是：如何组织执行流程、如何记录执行过程、如何评估结果质量、如何形成反馈闭环。

## 为什么值得拆

Harness Engineering 值得拆解的原因：

- **适合学习执行链路**：工程化 Agent 不是一次模型调用，而是一条完整执行链路
- **适合学习 Trace**：如何记录执行过程中的每一步，方便调试和优化
- **适合学习 Evaluator**：如何判断 Agent 的结果是否可靠，如何量化质量
- **适合学习反馈闭环**：如何从失败中获得改进信息，如何沉淀优化依据
- **适合学习工程化组织方式**：模块划分、配置管理、测试策略

## 推荐阅读顺序

1. **先看 README 和示例任务**：理解项目目标、使用方式和典型场景
2. **再看任务执行入口**：理解任务从哪里进入、如何被初始化
3. **再看执行过程如何记录**：理解 Trace 机制、哪些信息被记录、如何存储
4. **再看结果如何评估**：理解 Evaluator 机制、自动评测和人工评审
5. **再看失败样本如何处理**：理解失败记录、归因分析和优化闭环
6. **最后看测试、配置和扩展方式**：理解如何扩展新功能、如何配置参数

## 核心观察点

### Task / Run

任务和执行是两个不同层次的概念。Task 是用户请求，Run 是一次具体执行。

重点关注：Task 和 Run 的关系、一个 Task 是否可以多次 Run、Run 的状态如何管理。

### Executor

Executor 是实际执行任务的模块。

重点关注：Executor 如何接收任务、如何驱动执行、如何处理中间状态、如何生成最终结果。

### Trace

Trace 是执行过程的完整记录。Agent 项目需要记录执行过程，否则很难调试和优化。

重点关注：是否记录每一步的输入和输出摘要、是否记录工具调用参数和结果、是否记录状态变化、是否有唯一的执行 ID。

### Evaluator

评测机制可以帮助判断 Agent 的结果是否可靠。

重点关注：如何判断任务是否完成、如何判断结果是否符合预期、是否有自动评分、是否有人类反馈入口。

### Feedback

优秀的 Agent 系统不应该只执行一次，而应该能从失败中获得改进信息。

重点关注：失败是否会被记录、是否能生成改进建议、是否支持重新执行、是否能积累评测样本。

### Result

执行结果的结构化表示。

重点关注：结果包含哪些字段、是否有成功/失败标记、是否有执行摘要、是否关联 Trace。

### Error Handling

错误处理是工程化 Agent 的基本要求。

重点关注：错误类型有哪些、错误信息是否结构化、是否有重试机制、是否有降级策略。

### Test Case

测试用例是理解系统行为的重要参考。

重点关注：测试覆盖了哪些场景、测试用例的输入输出是什么、是否有边界案例测试。

## 可迁移设计

Harness Engineering 中值得迁移的设计思路：

- **为每次执行生成 run id**：唯一标识一次执行，方便关联 Trace、日志和评测结果
- **记录完整的执行轨迹**：记录输入、输出、工具调用记录、状态变化记录和关键决策摘要
- **执行结果和评估结果分离**：执行结果是 Agent 的输出，评估结果是对输出质量的判断，两者应该分开存储
- **失败样本沉淀为优化依据**：每次失败都应该被记录、归类、分析，转化为具体的优化行动
- **评测集防止回退**：用评测集持续监控质量，每次修改后用回归测试确保没有引入新问题

## 安全表述说明

在记录执行过程时，不使用"思考链""Chain-of-Thought""CoT""记录完整推理过程"等表述。统一使用：关键决策摘要、模型输出摘要、工具调用记录、状态变化记录、执行轨迹。

## 面试表达

可以这样表达：

> 我在学习 Harness Engineering 时，重点关注 Agent 工程化中的 Trace 和 Evaluation。因为 Agent 项目如果没有执行记录和质量评估，就很难从 Demo 走向可维护系统。我的理解是，Agent 不仅要能完成任务，还要能记录它怎么完成、哪里失败、后续如何改进。Trace 记录每次执行的完整轨迹，Evaluator 量化结果质量，失败样本沉淀为优化依据——这三者构成了 Agent 工程化的闭环。

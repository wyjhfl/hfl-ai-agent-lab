# Hermes Agent 源码拆解

## 项目定位

Hermes Agent 作为 Agent 执行链路的学习对象，用于观察一个 Agent 系统如何从任务输入走向工具调用和结果输出。

拆解它的重点不在于逐行阅读源码，而在于理解：Agent 如何接收任务、如何维护上下文、如何选择工具、如何执行动作、如何返回结果。

## 为什么值得拆

Hermes Agent 值得拆解的原因：

- **适合观察 Agent 入口**：理解任务从哪里进入系统、输入如何被封装
- **适合观察任务规划**：Agent 如何把用户请求转化为可执行步骤
- **适合观察工具调用**：工具如何注册、如何被选择、参数如何生成、结果如何回填
- **适合观察状态维护**：Agent 如何在多步执行中保持上下文
- **适合观察错误处理**：工具调用失败后如何处理、是否有重试和降级

## 推荐阅读顺序

1. **先找项目 README**：明确项目目标、启动方式和整体架构说明
2. **再找应用入口**：理解任务从哪里进入系统、入口函数接收什么参数
3. **再找 Agent 主循环或执行器**：理解任务如何被驱动执行、是否有循环或递归
4. **再找工具注册与调用逻辑**：理解工具如何被定义、如何被选择、如何被执行
5. **再找状态、记忆或上下文管理**：理解执行过程中的数据如何保存和传递
6. **最后看错误处理和测试用例**：理解系统如何处理异常、测试覆盖了哪些场景

## 核心观察点

### Agent 入口

首先要找到 Agent 的启动入口，理解系统是如何接收用户输入的。

重点关注：输入参数是什么、是否有统一的任务对象、是否有运行上下文、是否有状态初始化过程。

### 任务对象

用户输入通常会被封装成任务对象。任务对象是整个执行链路的数据载体。

重点关注：任务对象包含哪些字段、是否有任务 ID、是否有状态字段、是否有时间戳。

### Planner / Executor 是否分离

Agent 通常不会直接执行用户请求，而是先把请求转化为可执行步骤。

重点关注：是否有 Planner、是否区分计划和执行、是否支持多步骤任务、是否支持中间状态记录。

### Tool Registry

工具调用是 Agent 从"聊天"走向"执行"的关键。

重点关注：工具如何注册、工具如何被选择、工具参数如何生成、工具结果如何返回给 Agent。

### Tool Result

工具执行结果需要结构化保存，而不是直接丢弃。

重点关注：结果是否有固定格式、是否包含成功/失败标记、是否包含错误信息、是否能被后续步骤引用。

### State / Memory

一个工程化 Agent 需要保存执行过程，而不是每一步都无状态运行。

重点关注：是否维护 memory、是否维护 task state、是否记录 observation、是否记录 tool result。

### Retry / Fallback

真实系统中工具调用可能失败，模型输出也可能不稳定。

重点关注：是否有 retry、是否有 fallback、是否有异常捕获、是否有错误信息回传。

### Final Response

Agent 执行完成后如何生成最终响应。

重点关注：是直接返回模型输出还是经过后处理、是否包含执行摘要、是否包含来源引用。

## 可迁移设计

Hermes Agent 中值得迁移的设计思路：

- **任务对象封装**：把用户输入封装成任务对象，让整个执行链路有统一的数据载体
- **执行阶段拆分**：把 Agent 执行拆成计划、行动、观察、总结几个阶段，每个阶段有明确的输入输出
- **工具结果结构化**：工具调用结果要结构化保存，不要只取最终值
- **执行轨迹保留**：Agent 不应该只返回最终答案，还应该保留中间执行轨迹，方便调试和优化
- **错误可回溯**：错误信息要包含足够的上下文，方便定位问题

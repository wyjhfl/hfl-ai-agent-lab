# Hermes Agent 源码拆解

## 项目定位

Hermes Agent 在本知识库中被作为 Agent 执行链路的学习对象，用于观察一个 Agent 系统如何从用户输入走向任务规划、工具调用、状态维护和结果输出。

拆解它的重点不在于逐行阅读源码，而在于理解：Agent 如何接收任务、如何维护上下文、如何选择工具、如何执行动作、如何返回结果。这些是任何 Agent 系统都需要解决的核心问题。

## 架构总览

从通用 Agent 系统角度，Hermes Agent 可以拆成以下模块。这些是当前拆解视角，不代表已经确认真实源码类名：

- **输入接入层**：接收用户输入，封装成任务对象
- **Agent Runtime**：Agent 的主执行循环，驱动整个任务流程
- **Planner**：把用户请求转化为可执行步骤
- **Executor**：执行具体步骤，调用工具
- **Tool Registry**：工具注册、描述和管理
- **Memory / State**：保存执行过程中的上下文和状态
- **Prompt Builder**：把任务上下文、工具描述、历史信息组装成模型输入
- **Result Formatter**：把执行结果格式化为最终输出
- **Error Handler**：处理工具调用失败、模型输出异常等情况

## 核心运行链路

Hermes Agent 的核心运行链路可以描述为以下流程：

1. **用户输入任务**：用户提交一个任务请求
2. **构造任务对象**：把用户输入封装成结构化的任务对象，包含任务 ID、输入参数、上下文信息
3. **生成执行计划**：Planner 分析任务，生成可执行步骤列表
4. **选择工具**：根据当前步骤，从 Tool Registry 中选择合适的工具
5. **执行工具调用**：Executor 调用工具，传入参数，获取结果
6. **观察工具结果**：检查工具返回的结果，判断是否成功
7. **更新状态或记忆**：把工具结果保存到 Memory / State 中，供后续步骤使用
8. **判断是否继续**：检查是否还有未执行的步骤，或者是否已经完成任务
9. **生成最终输出**：Result Formatter 把执行结果格式化为用户可读的输出

这个流程体现了 Agent 的核心循环：计划、执行、观察、决策。

## 关键模块拆解

### Agent 入口

Agent 入口是任务进入系统的第一站。重点关注：

- 任务从哪里进入系统
- 输入如何被标准化为任务对象
- 上下文如何初始化
- 是否有统一的任务 ID 和状态字段

一个好的入口设计应该让后续模块不需要关心输入的具体格式，只需要处理标准化的任务对象。

### Planner

Planner 负责把用户请求转化为可执行步骤。重点关注：

- 任务是否被拆成多个步骤
- 计划和执行是否分离
- 是否支持动态调整计划
- 是否有步骤依赖关系

计划和执行分离是 Agent 设计的关键原则。Planner 只负责规划，不负责执行；Executor 只负责执行，不负责规划。这让两个模块可以独立演进。

### Tool Registry

工具调用是 Agent 从"聊天"走向"执行"的关键。重点关注：

- 工具如何注册：是否有统一的注册接口
- 工具如何描述：是否有 JSON Schema 描述参数
- 工具如何被选择：是模型选择还是规则匹配
- 工具如何被调用：参数如何生成，结果如何返回

工具注册应该包含：工具名称、描述、参数 Schema、返回值格式。这让模型能够理解工具的用途和使用方式。

### Tool Result

工具执行结果需要结构化保存。重点关注：

- 结果是否有固定格式
- 是否包含成功/失败标记
- 是否包含错误信息
- 是否能被后续步骤引用

结构化的工具结果是 Agent 状态管理的基础。没有结构化结果，Agent 就无法可靠地判断工具是否成功、如何处理失败。

### Memory / State

一个工程化 Agent 需要保存执行过程中的状态。重点关注：

- 是否维护 memory：保存历史对话和工具结果
- 是否维护 task state：保存当前任务的执行状态
- 是否记录 observation：保存对工具结果的观察
- 是否记录 tool result：保存工具调用的完整记录

状态管理决定了 Agent 能否处理多步骤任务。没有状态管理，Agent 只能处理单轮对话。

### Prompt Builder

Prompt Builder 负责把各种信息组装成模型输入。重点关注：

- 系统提示如何定义
- 任务上下文如何注入
- 工具描述如何格式化
- 历史信息如何压缩

Prompt Builder 的质量直接影响模型的输出质量。好的 Prompt Builder 应该让模型清楚地知道：自己是谁、要做什么、有哪些工具可用、之前做了什么。

### Error Handler

真实系统中工具调用可能失败，模型输出也可能不稳定。重点关注：

- 是否有重试机制
- 是否有降级策略
- 错误信息是否结构化
- 错误是否能被后续步骤处理

错误处理是 Agent 从 Demo 走向生产的关键。没有错误处理的 Agent 只能在理想条件下工作。

## 关键设计思想

### 用户输入封装成任务对象

把用户输入封装成任务对象，让整个执行链路有统一的数据载体。任务对象应该包含：任务 ID、输入参数、上下文信息、状态字段、时间戳。

### 计划、执行、观察、总结分离

Agent 执行应该拆成四个阶段：计划（Plan）、执行（Act）、观察（Observe）、总结（Summarize）。每个阶段有明确的输入输出，模块之间通过数据传递而不是直接调用。

### 工具调用结果结构化

工具调用结果要结构化保存，不要只取最终值。结构化结果包含：成功/失败标记、结果数据、错误信息、执行时间。这为后续的状态管理和错误处理提供基础。

### 保存执行轨迹

Agent 不应该只返回最终答案，还应该保留中间执行轨迹。执行轨迹包含：每一步的输入输出摘要、工具调用记录、状态变化记录、关键决策摘要。这为调试和优化提供依据。

### 错误可回溯

错误信息要包含足够的上下文，方便定位问题。错误信息应该包含：错误类型、错误描述、发生位置、相关输入、建议处理方式。

## 可迁移到自己项目的设计

从 Hermes Agent 中可以迁移以下设计到自己的项目：

- **任务对象封装**：把用户输入封装成任务对象，让整个执行链路有统一的数据载体
- **计划执行分离**：Planner 和 Executor 分离，各自独立演进
- **工具 Schema 驱动**：用 JSON Schema 描述工具参数，让模型能理解工具的使用方式
- **结构化工具结果**：工具调用结果包含成功/失败标记、结果数据、错误信息
- **执行轨迹保留**：记录每一步的输入输出摘要、工具调用记录、状态变化记录
- **Prompt 模板化**：系统提示、工具描述、任务上下文分开管理，按需组装
- **错误分级处理**：区分可重试错误和不可重试错误，分别处理

## 面试表达

### 表达一：整体理解

> 我在阅读 Hermes Agent 时，重点关注的不是某个函数怎么写，而是它如何把用户请求转化为一个可执行任务链路。一个可用的 Agent 系统至少要包含任务输入、计划生成、工具调用、状态维护和结果总结几个核心部分。源码拆解的价值在于理解模块之间的依赖关系和数据流转方式，这些设计思路可以直接迁移到自己的项目中。

### 表达二：设计思想

> 我从 Hermes Agent 中学到的最重要的设计思想是"计划、执行、观察、总结"的分离。Planner 只负责规划，Executor 只负责执行，两者通过任务对象传递数据。这种分离让系统更容易测试和扩展：可以单独测试 Planner 的规划质量，也可以单独测试 Executor 的执行能力。工具调用结果的结构化也很关键，它让 Agent 能够可靠地判断工具是否成功、如何处理失败。

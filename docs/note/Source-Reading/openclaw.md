# OpenClaw 架构拆解

## 项目定位

OpenClaw 适合用来学习复杂 Agent 系统的分层设计、模块边界、多 Agent 协作和工具抽象。

拆解 OpenClaw 时，重点不是一开始陷入所有源码细节，而是先理解整体结构：系统分几层、Agent 如何协作、工具如何接入、状态如何流转、任务如何结束。

## 为什么值得拆

OpenClaw 值得拆解的原因：

- **适合学习系统分层**：复杂 Agent 项目如何拆成多个层次，降低耦合
- **适合学习多 Agent 协作**：多个 Agent 如何有规则地协作，而不是自由对话
- **适合学习工具层抽象**：工具如何统一封装、参数如何结构化、结果如何标准化
- **适合学习状态流转**：多 Agent 之间如何共享状态、状态如何在节点间传递
- **适合学习复杂系统如何解耦**：模块之间如何定义接口、如何降低依赖

## 推荐阅读顺序

1. **先看 README 和整体介绍**：理解项目目标、使用场景和整体架构
2. **再看目录结构，判断系统分层**：从目录结构推断系统的模块划分
3. **再找任务入口**：理解任务从哪里进入系统、入口如何初始化
4. **再看 Agent 编排方式**：理解多个 Agent 如何协作、谁调度谁、谁先谁后
5. **再看工具层抽象**：理解工具如何注册、如何调用、结果如何标准化
6. **再看状态管理**：理解状态对象如何设计、如何在 Agent 间传递
7. **最后看评测、测试和扩展点**：理解如何扩展新功能、如何验证系统行为

## 核心观察点

### 接入层

接入层负责接收外部请求并转化为系统内部的任务对象。

重点关注：接入方式（API、CLI、消息队列）、输入格式、请求校验、会话管理。

### Agent 层

Agent 层是系统的核心，负责任务理解、规划和执行。

重点关注：Agent 如何定义、Agent 之间如何协作、是否有 Supervisor 或 Planner、调度逻辑在哪里。

### Tool 层

工具层决定 Agent 是否能真正执行任务。

重点关注：工具是否统一封装、工具参数是否结构化、工具结果是否标准化、是否支持错误处理。

### State 层

多 Agent 系统必须维护共享状态，否则不同 Agent 之间无法稳定协作。

重点关注：状态对象包含什么字段、Agent 如何读写状态、状态是否能恢复、状态是否能用于调试。

### Evaluation 层

评测层用于判断系统输出是否可靠。

重点关注：是否有自动评测、是否有人工评审、评测结果如何反馈到系统、是否有评测集管理。

### 配置层

配置层管理系统参数、模型配置、工具配置等。

重点关注：配置是否和代码分离、是否支持不同环境的配置、是否有默认值。

### 扩展点

扩展点决定了系统的可维护性和可扩展性。

重点关注：如何新增 Agent、如何新增工具、如何新增评测指标、扩展是否需要修改核心代码。

## 可迁移设计

OpenClaw 中值得迁移的设计思路：

- **清晰分层**：将复杂 Agent 系统拆成接入层、Agent 层、工具层、状态层、评测层，每个层次职责明确
- **职责单一**：每个 Agent 只负责一个明确职责，不要让一个 Agent 做所有事
- **状态串联**：使用状态对象串联多步骤任务，所有 Agent 共享同一个状态对象
- **工具标准化**：工具调用结果标准化，包含成功/失败标记、结果数据、错误信息
- **执行轨迹保留**：为调试和评测保留执行轨迹，记录关键决策摘要和状态变化
- **流程可控**：避免多个 Agent 自由对话导致流程失控，用调度机制控制流转顺序

## 面试表达

可以这样表达：

> 我在拆解 OpenClaw 时，重点关注它如何把复杂 Agent 系统拆成多个层次。我的理解是，多 Agent 项目不能只是多个角色的 Prompt 拼接，而应该有明确的调度逻辑、状态流转、工具接口和结果评估机制。系统分层的好处是每个模块只负责自己的职责，扩展时不需要修改核心代码。这种设计思路可以直接迁移到自己的项目中。

# RAG 工程化

## 这一节解决什么问题

RAG（检索增强生成）的 Demo 通常只有几行代码——把文档切一切、存进向量库、检索一下、拼进 Prompt。但要做到生产可用，需要处理文档解析、分块策略、向量检索质量、重排序、上下文管理、引用来源、检索评估等一系列工程问题。

RAG 工程化不是"接一个向量库就结束"。每个环节都影响最终的回答质量，任何一个环节出问题都会导致"能跑但回答质量差"的情况。

本节会系统讲解 RAG Pipeline 的各个环节、工程化要点和常见问题。

## 核心概念

### RAG 是什么

RAG（Retrieval-Augmented Generation，检索增强生成）是一种让大模型基于外部知识库回答问题的方法。核心思路是：先从知识库中检索相关文档片段，再把检索结果拼入 Prompt，让模型基于这些信息生成回答。

RAG 和普通 LLM 问答的区别：普通问答依赖模型自身的知识（可能过时、可能不准确、可能没有领域知识），RAG 则让模型"先查资料再回答"，显著提升回答的准确性和时效性。

### Pipeline 全景

```text
原始文档 → 解析 → 切分 → 向量化 → 存储 → 检索 → 重排序 → 上下文组装 → LLM 生成
```

每个环节都有独立的工程问题，下面逐一说明。

### 文档解析

需要处理多种格式：PDF、Word、Markdown、HTML、纯文本。每种格式都有自己的解析难点。

PDF 的难点在于表格提取、多栏排版、扫描件 OCR。Word 的难点在于样式和嵌入对象。HTML 的难点在于去除导航、广告等无关内容，只保留正文。

解析阶段还要保留元数据：文档标题、来源、页码、章节。这些元数据在后续的引用来源和检索过滤中会用到。

### 文本切分

切分策略直接影响检索质量。切太大，检索结果包含大量无关信息；切太小，丢失上下文。

常用方法：

- **按段落切分**：简单但不均匀
- **按句子切分**：粒度细但可能破坏语义
- **滑动窗口**：相邻块有重叠，保留上下文
- **语义切分**：用模型判断语义边界，效果好但成本高

关键原则：块大小要适中（通常 200-1000 token）、保留元数据（来源、页码）、处理好块之间的边界（不要把一句话切成两半）、相邻块可以有适当重叠。

### Embedding（向量化）

把文本块转化为向量表示，用于后续的相似度检索。选择 Embedding 模型要考虑：维度（影响存储和检索速度）、多语言支持（中文场景需要中文能力）、领域适配（通用模型 vs 领域微调模型）。

Embedding 的质量直接影响检索质量。同一个问题如果用不同的表述，好的 Embedding 模型应该能检索到相同的结果。

### 向量检索

基础是向量相似度搜索（余弦相似度、内积），但可以优化：

- **混合检索**：向量检索 + 关键词检索（BM25），两者结果融合
- **过滤条件**：按文档类型、时间范围、来源等条件过滤
- **分数阈值**：低于阈值的结果不返回，避免噪声

### 重排序（Reranking）

初步检索结果可能不够精准。用 Reranker 模型对结果二次排序，把最相关的结果排到前面。

Reranker 和 Embedding 的区别：Embedding 是双塔模型（文档和查询分别编码），速度快但精度有限；Reranker 是交叉编码器（文档和查询一起编码），精度高但速度慢。所以通常先用 Embedding 做粗筛（取 top 20），再用 Reranker 做精排（取 top 5）。

### 上下文组装

把检索到的块组装成 LLM 能理解的上下文。需要控制总长度（不能超过模型上下文窗口）、保留来源引用（方便用户验证）、处理重复内容（多个块可能包含相同信息）。

上下文组装的格式也很重要。清晰的分隔符、来源标注、块编号能让模型更容易理解和引用。

### 引用来源

RAG 的一个重要优势是回答可追溯。每个回答都应该标注信息来源，让用户能验证回答的准确性。

引用来源需要在切分阶段就保留元数据（文档名、页码、章节），在组装阶段标注来源，在生成阶段让模型引用。

### 检索质量评估

需要量化评估 RAG 的检索质量，常见指标：

- **召回率**：相关文档是否被检索到
- **精准率**：检索结果中有多大比例是相关的
- **MRR（Mean Reciprocal Rank）**：第一个相关结果排在第几位
- **端到端准确率**：最终回答是否正确

评估需要标注数据——一组问题和对应的正确文档。没有标注数据，评估就是盲目的。

## 为什么重要

RAG 工程化在 AI 应用中的价值体现在多个方面。

首先，**扩展模型知识**。模型自身的知识有截止日期，且可能缺少领域知识。RAG 让模型能基于最新的、特定领域的知识库回答问题。

其次，**减少幻觉**。模型在没有足够信息时会编造答案。RAG 提供了真实的知识来源，显著减少幻觉。但如果检索质量差，反而会引入噪声导致更多幻觉。

再次，**可追溯性**。RAG 的回答可以标注来源，用户能验证信息的准确性。这是企业场景中的重要需求。

最后，**知识更新**。只需要更新知识库，不需要重新训练模型。这比微调模型更灵活、更快速。

## 工程化理解

从工程角度看，RAG 不是"接一个向量库就结束"，需要系统化的工程管理。

**Pipeline 可配置**：切分策略、Embedding 模型、检索参数、重排序模型都应该可配置，而不是硬编码。不同场景可能需要不同的配置。

**增量更新**：知识库会持续更新。需要支持增量索引（新文档加入后不需要重建整个索引）和文档版本管理（文档更新后旧版本应该被替换）。

**缓存策略**：相同或相似的查询可以缓存检索结果，减少向量检索的开销。但缓存失效策略要合理——知识库更新后缓存应该失效。

**监控和告警**：需要监控检索质量（召回率、精准率）、延迟、错误率。质量下降时应该自动告警。

**失败处理**：检索可能失败（向量库不可用）、检索结果可能为空、上下文可能超长。每种失败都需要有合理的降级策略。

## 常见误区

**误区一：接一个向量库就结束**

向量库只是 RAG Pipeline 的一个环节。文档解析、切分策略、重排序、上下文组装、引用来源、质量评估都是工程化的必要组成部分。

**误区二：切分策略不重要**

切分太大导致噪声过多，切分太小导致上下文丢失。切分策略直接影响检索质量，需要根据具体场景调优。

**误区三：不需要重排序**

向量检索的排序不够精准。没有重排序，最相关的结果可能排在后面，被截断后无法进入上下文。

**误区四：不需要评估**

没有评估就不知道 RAG 的效果到底好不好。需要有标注数据和量化指标，持续监控检索质量。

**误区五：知识库不需要维护**

文档会过时、会更新、会新增。没有增量更新和版本管理，知识库会越来越不准确。

## 面试表达

可以这样表达：

> RAG 不只是"把文档切一切然后检索"。我关注的是整个 Pipeline 的工程化：文档解析要处理多种格式，切分要平衡块大小和语义完整性，检索要支持混合搜索和过滤，重排序要提升精准度，最后上下文组装要控制长度并保留来源。每个环节都会影响最终的回答质量。另外，RAG 系统需要持续评估——用标注数据量化召回率和精准率，发现质量下降时及时排查。没有评估的 RAG 系统，效果好不好全靠猜。
